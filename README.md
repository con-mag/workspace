# المركز — النسخة الأخيرة

هذه النسخة تفصل بين:

1. **الواجهة:** `site/` وتُنشر على GitHub Pages.
2. **بوابة الحفظ:** `api/` وتُنشر كـServerless API، مثل Vercel.
3. **مخزن النسخة المشتركة:** مستودع GitHub نفسه.

الواجهة لا تحتوي GitHub Token ولا Secret. عمليات الكتابة والحذف تمر عبر API خادمي محمي، ثم تُحفظ كملفات/بيانات حقيقية في المستودع.

## ماذا تغير؟

- عودة إلى طابع بصري هادئ قريب من هوية النسخة السابقة: كريمي/رمادي فاتح مع أزرق داكن مائل للنيلي وبنفسجي مطفأ، مع إضاءة أيقونات محسوبة.
- `محفظة العملاء` أصبحت `مكتبة العملاء`؛ كل عميل بوابة إلى مساحة ملفات حقيقية.
- ريتاج موجودة كأول عميلة، مع الهيكل الأصلي الفعلي المستخرج من المرفق داخل `site/clients/ريتاج علي/`.
- المجلدات تُعرض كبطاقات/أيقونات؛ النقر عليها يدخل للمجلد.
- يمكن إنشاء مجلد، إنشاء TXT/MD، أو رفع DOCX وغيرها.
- يمكن تحرير ملفات النصوص وحفظها.
- يمكن حذف الإضافات الجديدة من مساحة العميل بعد التحقق.
- الإضافات العامة قابلة للحذف أيضًا.
- الأجهزة الأخرى ترى النسخة المشتركة نفسها بعد التحديث؛ ويوجد فحص دوري كل 15 ثانية في الواجهة عند اتصال الـAPI.

## ملاحظة عن المزامنة

هذا النظام يستخدم GitHub API كمخزن مشترك، وليس WebSocket/Realtime. لذلك «المزامنة» هنا تعني أن كل الأجهزة تقرأ أحدث نسخة من المستودع؛ والأجهزة المفتوحة تعيد الفحص دوريًا. هذا يناسب GitHub Pages مع بنية بسيطة قابلة للتدقيق.

## إعداد API

انشر `api/` على Vercel، ثم ضع المتغيرات:

```text
GITHUB_OWNER=...
GITHUB_REPO=...
GITHUB_BRANCH=main
GITHUB_TOKEN=...
ADMIN_PASSWORD=1122
SESSION_SECRET=...
ALLOWED_ORIGIN=https://YOURNAME.github.io
```

### GitHub Token

أنشئ Fine-grained Personal Access Token مخصصًا للمستودع المطلوب فقط، مع `Contents: Read and write` فقط. GitHub توصي باستخدام أقل صلاحيات ممكنة والحفاظ على بيانات الاعتماد خارج الواجهة.

### الواجهة

في `site/js/config.js`:

```js
window.APP_CONFIG = Object.freeze({
  API_BASE: "https://YOUR-API.vercel.app/api",
  POLL_MS: 15000,
  APP_NAME: "المركز"
});
```

لا تضع Token أو Secret أو كلمة مرور في هذا الملف.

## لماذا ليس GitHub Token مباشرة في الموقع؟

لأن أي قيمة سرية موضوعة في JavaScript المتاح للزوار يمكن استخراجها. GitHub توصي بحماية بيانات الاعتماد واستخدام أقل الصلاحيات، كما أن Create/Update File Contents يتطلب صلاحية Contents: write على token مناسب.

## كلمة 1122

يُطلب من المستخدم إدخالها عند الكتابة/التعديل/الحذف، وتُرسل مرة إلى API للتحقق منها، ثم تحصل الواجهة على جلسة مؤقتة موقعة. لا تُحفظ الكلمة في JavaScript.

لكن لا يمكن وصف كلمة مرور من أربعة أرقام بأنها حماية قوية ضد التخمين المتعمد. يمكن تغيير `ADMIN_PASSWORD` إلى كلمة أقوى لاحقًا.

## إذا ظهرت رسالة «كلمة المرور غير صحيحة» قبل ربط API

في النسخة المحلية، إذا كان `site/js/config.js` يحتوي `API_BASE: ""` فلن يتم إرسال كلمة المرور إلى الخادم أصلًا؛ الواجهة ستوضح الآن أن الربط غير مكتمل بدل وصف الحالة بأنها كلمة مرور خاطئة. كلمة `1122` تُتحقق منها على الخادم فقط بعد نشر API وضبط `ADMIN_PASSWORD=1122`.
